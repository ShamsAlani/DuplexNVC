# Cross-chip study (contribution C3)

**Question:** do the baseline's results and its explanations hold on other Apple Silicon Macs, and how does the best setting change from one chip to the next? The same runs as the baseline are repeated on each Mac with the same models, the same bitstreams and the same protocol, and compared with Shams's reference M4 Pro and with the MLVC paper's M3 Pro.

| Mac | Owner | Role |
|---|---|---|
| MacBook Pro 14-inch, M4 Pro, 24 GB | Shams | Reference: the baseline in [`../baseline/`](../baseline/) |
| MacBook Pro 16-inch, M4 Max | Warda | Same generation and the same Neural Engine as the M4 Pro (16 cores, 38 TOPS), but more memory bandwidth, more GPU cores and the larger 16-inch chassis (more cooling, High Power mode): if the NE times match the M4 Pro, the NE itself sets the speed, not memory or cooling |
| MacBook Pro 13-inch, M1 | Mohammed | Oldest generation |
| M3 Pro | MLVC paper | NE times taken from the paper (each network alone) |

Exact specs of every Mac are in `results/<mac>/specs.txt`, written by `cc_specs`.

## What is measured on each Mac

| Part | What | Same as | Why it matters |
|---|---|---|---|
| decode | Shams's bitstreams decoded on the NE (twice), GPU and CPU; B\*'s incoming stream re-encoded on the NE | experiment 04 | In a real call the two ends are different Macs. Are the NE decodes bit-identical across Macs? Is the encoder deterministic across Macs? |
| bstar | B\*: 5 unpaced rounds (each network alone, turns, duplex), 5 paced duplex, 3 paced turns, 3 CLI runs | experiment 03 (`./x`) | Each network's time alone, the sharing speedup S, the slowest frames at 30 fps |
| energy | 120 s idle, 5 paced B\* runs with `powermetrics` | experiment 06 (`./w`) | Energy per frame pair, per processor |
| contention | Memory-bandwidth load from the CPU at 0 / 25 / 50 / 75 % of the measured peak while one network runs alone on the NE (full MLVC 360p and 720p, 2 rounds) | new | If a network slows down as load grows, memory bandwidth limits it; if not, the NE itself does. Explains why the two networks barely overlap on the NE |
| settings | The 7 model/resolution settings: each network alone on the NE, the encoder alone on the GPU, and the two placements that won on the reference Mac (NE–NE and GPU–NE) at 30 fps, with 15 fps runs if 30 fps fails | experiment 09 (`./all`), shortened | Which setting and placement is best on this chip, and why |

Every run uses the baseline's quiet mode, 60 s runs with 60 s rest, the first 64 frames discarded, and the same rules (a placement meets 30 fps if fewer than 1 % of frames are late or dropped in each direction). Every number is computed with the baseline's own tools (`analyze_run.py`, the same medians as `sum.py` and `step4_sum.py`). Run on the reference Mac's own raw data, the summary reproduces the published baseline tables exactly (ratio 1.000).

To fit one night, the settings part uses 2 unpaced rounds and 3 paced runs per placement (the reference used 3 and 5) and runs only the two placements that won on the reference Mac. B\* and its energy use the full protocol.

The contention load is generated by the CPU (`bwload.c`: threads copying between 96 MB buffers, rate-limited). The percentages are of the peak the CPU reaches on that Mac, not of Apple's published bandwidth, and two cores are left free for the benchmark itself.

## How to run

**Shams (reference Mac), once:**
```bash
cd ~/DuplexNVC && git pull
bash cross_chip/scripts/cc_specs     # specs of this Mac (20 s)
bash cross_chip/scripts/cc_pack      # bundles + bitstreams + source clips + reference MD5s -> ~/Downloads/cc_pack_shams.zip (10 min)
```
Upload `cc_pack_shams.zip` to the shared Drive folder.

**Every other Mac (Warda's M4 Max, Mohammed's M1):** put `cc_pack_shams.zip` in Downloads, Wi-Fi on, charger in, then one command:
```bash
bash ~/DuplexNVC/cross_chip/scripts/cc_go
```
For the generational comparison only (about 40 min of runs instead of 7 h), use `bash ~/DuplexNVC/cross_chip/scripts/cc_gen` instead: B\* (each network alone, turns, duplex, 2 rounds; paced 30 fps, 3 runs with energy) and the other 6 settings (each network alone on the NE, 1 round), with 30 s rests.

It asks for the Mac password, a GitHub sign-in (first time only) and one quiet-mode checklist, all in the first minutes. Then it runs alone: setup (`cc_setup`), specs (`cc_specs`), Wi-Fi and Bluetooth off, every run (`cc_all`, about 7 h), Wi-Fi back on, results pushed (`cc_collect`). If it stops, the same command continues where it stopped. The parts can also be run one by one: `cc_all mon` runs only B\*, energy and the settings (about 5.5 h); `cc_all tue` runs only the decode check and contention (about 1.5 h).

## Files

| File | What |
|---|---|
| `scripts/cc_gen` | Generational comparison only, in one command (about 40 min of runs) |
| `scripts/cc_go` | Everything in one command on a second Mac: setup, specs, quiet mode, all runs, push |
| `scripts/cc_specs` | Every spec we compare: chip, CPU/GPU cores, memory and its bandwidth (Apple's figure and measured), macOS, Energy Mode, charger, battery, thermal state |
| `scripts/cc_pack` | Run on the reference Mac: packs its bundles, bitstreams, source clips and reference MD5s |
| `scripts/cc_setup` | One-time setup on another Mac (tools, libmlvc at `eb5d60a`, measurement program, the reference Mac's pack, streams checked by MD5, smoke test) |
| `scripts/cc_all` | All runs, unattended and resumable |
| `scripts/bwload.c` | Memory-bandwidth load for the contention part |
| `scripts/cc_sum.py` | Summary of one Mac against the reference M4 Pro and the M3 Pro |
| `scripts/cc_compare.py` | Every Mac side by side: `results/all_macs.csv` |
| `scripts/cc_collect` | Copies the results into `results/<mac>/`, zips the raw data, pushes |
| `results/<mac>/` | `bstar_compare.csv`, `alone_compare.csv`, `placements_compare.csv`, `contention.csv`, `decode.csv`, `summary.txt`, `specs.txt`, `logs/` |
| `results/all_macs.csv` | One row per metric, one column per Mac |

Raw data (every run's `frames.csv`, `run.txt`, `power.txt` and logs) is in `cc_raw_<mac>.zip` on the shared Drive.
